2.1 Understanding of the assignment

Transform Health's existing assessment tool provides a structured process for reviewing national health data governance legislation and regulation against the Health Data Governance Principles and Legislative Blueprint.

The current workflow requires significant manual effort in:

  1. Reviewing uploaded legislative and regulatory documents
  2. Mapping relevant provisions against the Principles and their standard interpretations
  3. Populating the Step 2 assessment worksheet
  4. Producing the Step 3 summary and country-level findings

The proposed feature should automate the repetitive evidence-extraction work while preserving human control, traceability and accuracy.

The system should therefore not be designed as a legal interpretation engine. It should be designed as:

An evidence-grounded document extraction and structured assessment assistant that produces a draft for human verification.

The system must not:

  • Invent legislative provisions
  • Paraphrase source text as if it were a legal finding
  • Present unsupported interpretations
  • Hide the location or origin of extracted evidence
  • Treat AI-generated content as final without human review

2.2 Proposed architecture

The processing service should be separated from WordPress. WordPress would provide the user interface, access control and upload/download experience, while a separate processing API or worker environment would handle document analysis.

This separation reduces risk to the existing WordPress installation and allows the processing infrastructure to be scaled or replaced independently.

2.3 Proposed processing workflow

Stage 1: Registration and access approval

Users would:

  1. Request access
  2. Provide required registration information
  3. Accept terms concerning document storage, processing and output use
  4. Receive approval or rejection
  5. Access the assessment interface after approval

The registration and consent design would be agreed during the orientation phase.

Stage 2: Upload and validation

The user uploads:

  • The completed Step 1 worksheet
  • Relevant legislative and regulatory documents
  • Supporting metadata such as country, document type, language and date

The system validates:

  • File type
  • File size
  • Number of documents
  • Total page count
  • Language
  • Duplicate uploads
  • Machine readability
  • Required worksheet structure

Scanned or non-machine-readable documents should not silently fail. The system should show a clear status such as:

This document could not be processed as machine-readable text. Please provide a text-readable version or request OCR processing if enabled.

Stage 3: Document processing

The system would:

  1. Extract text from each document
  2. Preserve document identity and page/section information
  3. Detect language
  4. Divide text into retrievable sections
  5. Compare relevant sections against the Health Data Governance Principles and Legislative Blueprint
  6. Identify potentially relevant source passages
  7. Return verbatim extracts with citations

Stage 4: Evidence extraction

Each Step 2 record should use a structured schema similar to:

{
  "principle_id": "HDG-01",
  "core_element_id": "HDG-01-03",
  "status": "identified",
  "verbatim_extract": "...exact text from source document...",
  "source_document": "National Health Data Governance Act.pdf",
  "page": 27,
  "section": "Section 4.2",
  "language": "en",
  "evidence_location": "Page 27, Section 4.2",
  "verification_status": "pending_human_review"
}

The fields for source document, location and verbatim extract should be mandatory.

If supporting evidence is not found, the system should return:

{
  "status": "not_identified",
  "verbatim_extract": null,
  "verification_status": "pending_human_review"
}

The system must not force an answer when evidence is absent.

2.4 Hallucination and unsupported-output safeguards

The following safeguards are proposed:

Evidence-first extraction

The system may only return a finding where it can identify a supporting passage in an uploaded document.

Mandatory citations

Every extracted passage must include:

  • Source document
  • Page number where available
  • Section or article reference where available
  • Original language
  • Exact text location

Verbatim validation

After extraction, the system should check that the returned text exists in the source document. This can use:

  • Exact string matching
  • Normalised whitespace matching
  • Character-level similarity checks where formatting differences occur

Records that fail citation or text verification should be marked for review or rejected from the draft output.

No unsupported interpretation fields

The Step 2 output should not include unrestricted narrative fields that encourage the model to interpret legislation. It should focus on:

  • Principle
  • Core element
  • Status
  • Verbatim evidence
  • Citation
  • Verification state
  • Notes for human review

Explicit "Not identified" state

Where no relevant evidence is found, the system should return "Not identified". It should not infer that a provision exists merely because a related concept appears elsewhere.

Human verification

All Step 2 and Step 3 outputs should remain drafts until reviewed and approved by an authorised user.

2.5 Step 3 deterministic summary generation

Step 3 should not rely on a second unconstrained language-model summary.

Instead, the summary should be generated from structured Step 2 records using deterministic rules.

For example:

Step 2 statusSummary treatment
IdentifiedCount as evidence found
Partially identifiedCount as partial coverage
Not identifiedCount as no evidence found
Pending reviewExclude from final summary and flag for review

The system could generate summaries such as:

Of the 12 assessed core elements under this Principle, 7 were identified, 3 were partially identified and 2 were not identified. Four records remain pending human verification.

The exact wording and aggregation rules would be agreed during the design phase and documented for auditability.

2.6 Multilingual processing

The initial version should support English, French and Spanish.

The proposed approach includes:

  • Language detection during upload
  • Language-aware document parsing
  • Language-specific retrieval and extraction prompts
  • Preservation of verbatim evidence in the original language
  • Citation to the original document and page
  • Output labels and guidance in the agreed interface language
  • Optional translation only where explicitly required and clearly marked as a translation

The original-language extract should remain the authoritative evidence. Translations must not replace the original citation.

2.7 Cost and token controls

Because the expected volume is low and intermittent, the system should prioritise cost-efficiency.

Proposed controls include:

  • Maximum number of documents per assessment
  • Maximum total page count
  • Maximum file size
  • Per-job token cap
  • Per-user usage quota
  • Maximum processing duration
  • Provider-level cost monitoring
  • Graceful termination when a limit is reached
  • Clear user notification when processing stops
  • Prompt caching for repeated reference materials
  • Batch processing where asynchronous workflows allow it

The system should record:

  • Token usage
  • Estimated cost
  • Processing time
  • Number of documents
  • Number of pages
  • Number of extracted records
  • Failure and retry information

2.8 Model- and provider-agnostic design

The architecture should separate:

  • Document parsing
  • Retrieval
  • Extraction schema
  • Validation
  • Summary rules
  • Model/provider adapter

This allows the underlying model provider to be changed without redesigning the assessment workflow.

A provider abstraction layer would allow the system to support different models while preserving the same:

  • Input format
  • Structured output schema
  • Citation requirements
  • Validation rules
  • Cost controls
  • Human review process

2.9 WordPress integration

The Health Data Governance website would provide:

  • Registration
  • Access request
  • Consent acknowledgement
  • Document upload
  • Assessment initiation
  • Processing status
  • Error notifications
  • Download links

The WordPress interface would communicate with the external processing service through authenticated API requests.

The workflow would be:

For the authenticated assessment workflow described above, an API-based integration is more appropriate than an iframe because the feature requires:

  • Authenticated user state
  • File uploads
  • Job tracking
  • Access control
  • Notifications
  • Secure downloads
  • Persistent assessment records

Embedding read-only views with an iframe. Where a self-contained, read-only view (such as a published country summary or a landscape map) needs to appear as a page within the Health Data Governance website, an iframe embedding approach can be used instead of, or alongside, the API integration. We have used this exact pattern on a WordPress site before: the AIxD Threat Map was embedded as an iframe into the Power for Democracies research portal — see powerfordemocracies.org/research/our-research/ai-democracy-landscape and the Work Samples page. An iframe isolates the embedded tool from the WordPress theme's CSS, requires no theme changes, and keeps the host site's performance and security unchanged.

2.10 Testing and evaluation

Testing should use an agreed sample of existing country assessments.

The evaluation framework should measure:

Extraction accuracy

  • Precision of identified evidence
  • Recall of relevant evidence
  • Citation accuracy
  • Verbatim fidelity
  • Correct principle/core-element mapping

Failure handling

  • Scanned documents
  • Unsupported formats
  • Oversized assessments
  • Missing worksheet fields
  • API or model failures
  • Token-cap termination

Security and privacy

  • Access control
  • User isolation
  • Secure file storage
  • Deletion requests
  • Expired links
  • Consent capture

Usability

  • Registration
  • Upload
  • Job status
  • Error messages
  • Downloads
  • Human verification flow

Cost and performance

For each test assessment, record:

  • Number of documents
  • Total pages
  • Processing time
  • Token consumption
  • Estimated cost
  • Number of records requiring review

2.13 Assumptions

The proposed fee assumes:

  • Transform Health provides access to the existing assessment tool and WordPress environment
  • Transform Health provides the Health Data Governance Principles, standard interpretations, Legislative Blueprint and existing assessment worksheets
  • Transform Health provides or approves a sample of existing country assessments for testing
  • The initial system operates at low and intermittent volume
  • Final hosting and model-provider costs are agreed during the design phase
  • The final system remains subject to human verification
  • Translation of source materials beyond the required processing interface is not included unless agreed
